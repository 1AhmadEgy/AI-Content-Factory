AI CONTENT FACTORY
CONTRACT SPECIFICATION
FILE: docs/contracts/01_RESULT_CONTRACT.txt

============================================================
1. PURPOSE
============================================================

This document defines the canonical Result contract used across
the AI Content Factory application.

The Result contract provides a unified mechanism for representing:

- Successful operations
- Failed operations
- Domain failures
- Persistence failures
- Network failures
- Provider failures
- Worker failures
- Validation failures
- QC failures
- License failures
- Hardware/resource failures
- Unknown failures

The contract MUST prevent uncontrolled exception propagation across
architectural boundaries.

Result is a cross-layer contract.

It MUST be usable by:

- Domain
- Application
- Data
- Infrastructure
- Backend
- Workers
- Providers
- Orchestrator
- Queue
- QC
- Rendering
- Publishing

============================================================
2. CANONICAL CONTRACT
============================================================

Canonical Kotlin definition:

sealed interface Result<out T> {

    data class Success<T>(
        val data: T
    ) : Result<T>

    data class Failure(
        val error: AppError
    ) : Result<Nothing>
}

============================================================
3. SUCCESS
============================================================

Success represents a completed operation whose expected output
exists and is valid according to the contract of that operation.

A Success MUST NOT be returned when:

- The operation is only partially complete
- The output has not been persisted
- The output cannot be verified
- Required QC has not passed
- A provider reported success but no usable artifact exists
- The job is still running
- The operation was cancelled
- Required dependencies failed

============================================================
4. FAILURE
============================================================

Failure represents an operation that could not produce its
contractually valid result.

Failure MUST contain an AppError.

Failure MUST NOT be represented using:

- null
- empty strings
- magic values
- boolean success flags
- arbitrary exceptions
- UI-specific error objects

============================================================
5. APP ERROR
============================================================

Canonical structure:

data class AppError(
    val category: ErrorCategory,
    val code: String,
    val message: String,
    val retryable: Boolean,
    val details: Map<String, String> = emptyMap(),
    val cause: Throwable? = null
)

The exact implementation MAY evolve, but the semantic contract
MUST remain stable.

============================================================
6. ERROR CATEGORIES
============================================================

Canonical categories:

- Validation
- Network
- Persistence
- Provider
- Worker
- QC
- License
- Hardware
- Unknown
- Authentication
- Authorization
- Conflict
- Timeout
- Cancellation
- Dependency
- Resource
- Configuration

No component may invent a new category locally without updating
the canonical error specification.

============================================================
7. ERROR CODE RULE
============================================================

Every Failure SHOULD contain a stable machine-readable code.

Examples:

VALIDATION_INVALID_INPUT
VALIDATION_REQUIRED_FIELD
PERSISTENCE_NOT_FOUND
PERSISTENCE_WRITE_FAILED
NETWORK_UNAVAILABLE
NETWORK_TIMEOUT
PROVIDER_UNAVAILABLE
PROVIDER_RATE_LIMITED
PROVIDER_INVALID_RESPONSE
WORKER_INITIALIZATION_FAILED
WORKER_EXECUTION_FAILED
QC_FAILED
LICENSE_UNKNOWN
LICENSE_BLOCKED
HARDWARE_INSUFFICIENT_VRAM
RESOURCE_OUT_OF_DISK
DEPENDENCY_FAILED
JOB_CANCELLED
JOB_TIMEOUT

Error codes are API/event/logging contracts.

Messages are NOT machine contracts.

Clients MUST branch on codes/categories rather than human-readable
messages.

============================================================
8. RETRYABLE FLAG
============================================================

Every operational failure MUST define whether retrying is allowed.

Examples:

NETWORK_TIMEOUT
    retryable = true

PROVIDER_UNAVAILABLE
    retryable = true

VALIDATION_INVALID_INPUT
    retryable = false

LICENSE_BLOCKED
    retryable = false

QC_FAILED
    retryable = usually false

HARDWARE_INSUFFICIENT_VRAM
    retryable = false unless routing can select another model

The retry engine MUST NOT guess retryability from message text.

============================================================
9. TRANSIENT VS PERMANENT FAILURES
============================================================

Failures SHOULD be classified conceptually as:

TRANSIENT

Examples:
- Network outage
- Temporary provider outage
- Queue timeout
- Temporary GPU allocation failure
- Temporary filesystem lock
- Rate limiting

PERMANENT

Examples:
- Invalid input
- Missing required entity
- Unsupported format
- Blocked license
- Missing mandatory model
- Impossible hardware requirement
- Invalid configuration

RECOVERABLE_BY_ROUTING

Examples:
- Model unavailable
- GPU memory insufficient for selected model
- Provider unavailable
- Unsupported capability

The Job Engine uses this classification to decide whether to:

- Retry
- Backoff
- Fallback
- Requeue
- Block
- Fail permanently

============================================================
10. RESULT OWNERSHIP
============================================================

Result MUST be interpreted at the layer that owns the operation.

Example:

Provider:
Result<ProviderOutput>

Worker:
Result<WorkerOutput>

Repository:
Result<Project>

UseCase:
Result<Project>

Orchestrator:
Result<GenerationJob>

UI:
Result SHOULD normally be transformed into a UI state rather than
passed directly to Compose components.

============================================================
11. EXCEPTION BOUNDARY
============================================================

Exceptions MAY exist internally.

Exceptions MUST NOT cross architectural boundaries uncontrolled.

Canonical flow:

Provider exception
        ↓
Provider adapter
        ↓
AppError
        ↓
Result.Failure
        ↓
Worker
        ↓
Job Engine

A provider-specific exception MUST NOT leak into Domain code.

============================================================
12. SECURITY
============================================================

AppError MUST NOT expose secrets.

Forbidden in messages, details, logs, API responses, or events:

- API keys
- Access tokens
- Refresh tokens
- Passwords
- Private keys
- Provider credentials
- Authorization headers
- Sensitive signed URLs

Errors MUST be sanitized before external exposure.

============================================================
13. USER-FACING MESSAGE
============================================================

Human-readable messages are presentation concerns.

Recommended architecture:

AppError
    ↓
ErrorTranslator
    ↓
Localized UI message

The Domain layer MUST NOT depend on Android string resources.

============================================================
14. RESULT VS JOB STATUS
============================================================

Result MUST NOT replace GenerationJob status.

Result answers:
"Did this function call succeed?"

GenerationJob answers:
"What is the lifecycle state of this asynchronous operation?"

A successful createJob call does NOT mean the generation succeeded.

============================================================
15. ASYNC OPERATIONS
============================================================

For asynchronous AI operations, an API request may return:

Result.Success(GenerationJob)

while the job is still:

CREATED
QUEUED

Actual generation result is reported later through:

- Job persistence
- REST polling
- WebSocket events
- Event consumers

Never return Success merely because a provider accepted a request.

============================================================
16. OUTPUT VERIFICATION
============================================================

For generation operations:

Provider success
        ≠
Application success

Application success requires, as applicable:

1. Provider returned successfully
2. Worker produced an output
3. Output exists
4. Output can be opened/read
5. Metadata is valid
6. Asset is persisted
7. Required provenance is persisted
8. Required QC passes
9. Job state is updated consistently

Only then may the operation become terminal COMPLETED.

============================================================
17. PARTIAL RESULTS
============================================================

Partial results MUST NOT be silently represented as Success.

If an operation intentionally supports partial output, the contract
MUST explicitly define it.

For GenerationJob execution, partial generation SHOULD normally be
represented as:

- intermediate asset
- checkpoint
- retryable execution state
- failed execution with preserved artifacts

rather than false Success.

============================================================
18. REPOSITORY RULE
============================================================

Repositories MUST return Result for operations that may fail.

Examples:

suspend fun getProject(id: String): Result<Project>
suspend fun createProject(project: Project): Result<Project>
suspend fun updateProject(project: Project): Result<Project>
suspend fun deleteProject(id: String): Result<Unit>

============================================================
19. PROVIDER AND WORKER RULES
============================================================

Providers MUST translate provider-specific failures into AppError.

Workers MUST return Result<WorkerOutput>.

Workers MUST provide enough information for the Job Engine to
classify retry, fallback, cancellation, blocking, or permanent
failure.

Workers MUST NOT independently implement global retry policy.

============================================================
20. QC, LICENSE AND HARDWARE RULES
============================================================

QC failures are valid failures and MUST prevent COMPLETED when QC
is mandatory.

UNKNOWN license status MUST NOT be treated as VERIFIED.

Hardware failures MUST remain distinguishable from provider failures
because they are inputs to Model Router decisions.

============================================================
21. CONFLICT AND NOT-FOUND RULES
============================================================

Concurrent modification MUST be explicit:

CONFLICT_VERSION_MISMATCH

Missing resources MUST use stable codes such as:

PERSISTENCE_PROJECT_NOT_FOUND

The UI may translate these codes into user-friendly messages.

============================================================
22. TRACEABILITY
============================================================

Failures SHOULD be traceable through:

Request ID
Execution ID
Job ID
Trace ID
Worker ID
Provider
Model

Canonical flow:

traceId
  ↓
jobId
  ↓
executionId
  ↓
workerId
  ↓
provider/model
  ↓
AppError

============================================================
23. API AND EVENT MAPPING
============================================================

API and event representations MUST use stable error codes.

Example API shape:

{
  "error": {
    "code": "PROVIDER_UNAVAILABLE",
    "category": "PROVIDER",
    "message": "Provider is temporarily unavailable",
    "retryable": true,
    "requestId": "...",
    "traceId": "..."
  }
}

Internal exceptions and stack traces MUST NOT be returned directly.

============================================================
24. IDEMPOTENCY AND RETRY
============================================================

Result handling MUST work correctly with idempotent operations.

A repeated request MUST NOT create inconsistent state merely because
the first attempt's response was lost.

Result.Failure does NOT itself trigger retry.

Retry policy belongs to the Job Engine / Scheduler.

Canonical flow:

Worker
  ↓
Result.Failure
  ↓
Job Engine classification
  ↓
retryable?
  ├── YES → RETRYING
  └── NO  → FAILED

============================================================
25. FALLBACK
============================================================

Fallback is controlled outside Result.

Example:

Provider A
  ↓
Failure(PROVIDER_UNAVAILABLE)
  ↓
Model Router
  ↓
Provider B
  ↓
execute

The original failure MUST remain auditable.

============================================================
26. CONTRACT EVOLUTION
============================================================

Non-breaking changes MAY include:

- Adding optional diagnostic fields
- Adding new error codes
- Adding optional metadata

Potentially breaking changes include:

- Removing categories
- Renaming error codes
- Changing Success semantics
- Changing Failure semantics
- Changing retryability semantics
- Removing required fields

Breaking changes require:

- version review
- migration plan
- affected consumer review
- tests
- documentation update

============================================================
27. FORBIDDEN PATTERNS
============================================================

The following are forbidden:

1. Returning null to indicate failure.
2. Returning false when a detailed failure is required.
3. Throwing arbitrary exceptions across layers.
4. Using UI strings as error codes.
5. Parsing error messages to determine behavior.
6. Treating every error as retryable.
7. Treating every provider success as application success.
8. Exposing secrets through errors.
9. Returning Success before persistence verification.
10. Returning Success before required QC.
11. Hiding provider identity from operational failures.
12. Silently converting permanent failures into retries.

============================================================
28. REQUIRED TESTS
============================================================

RESULT-001  Success contains expected data.
RESULT-002  Failure contains AppError.
RESULT-003  Error code remains stable.
RESULT-004  Retryable flag is preserved.
RESULT-005  Provider exception maps to Provider AppError.
RESULT-006  Network timeout maps to retryable network error.
RESULT-007  Validation failure is non-retryable.
RESULT-008  License blocked is non-retryable.
RESULT-009  Hardware failure is distinguishable from provider failure.
RESULT-010  QC failure prevents successful completion.
RESULT-011  Secrets are removed from external error representation.
RESULT-012  Error mapping preserves execution/job identifiers.
RESULT-013  Result does not imply asynchronous job completion.
RESULT-014  Repeated idempotent operation returns consistent result.
RESULT-015  Contract serialization remains backward compatible.

============================================================
29. ACCEPTANCE CRITERIA
============================================================

[ ] Result is defined centrally.
[ ] No production module creates an incompatible Result type.
[ ] AppError is centrally defined.
[ ] Error categories are canonical.
[ ] Error codes are machine-readable.
[ ] Retryability is explicit.
[ ] Exceptions do not leak across boundaries.
[ ] Provider failures are normalized.
[ ] Worker failures are normalized.
[ ] Repository failures are normalized.
[ ] QC failures are normalized.
[ ] License failures are normalized.
[ ] Hardware failures are normalized.
[ ] API errors use stable codes.
[ ] Events use stable error codes.
[ ] Secrets cannot leak through errors.
[ ] Async completion is not confused with function success.
[ ] Required tests pass.

============================================================
30. DEFINITION OF DONE
============================================================

The Result contract is DONE when:

- It is implemented in the canonical Core/Domain location.
- All major boundaries use it consistently.
- No legacy ad-hoc error mechanism remains in production paths.
- Provider exceptions are normalized.
- Worker failures are classifiable.
- Retry policy can consume AppError reliably.
- API serialization is stable.
- Event serialization is stable.
- Security review confirms no secret leakage.
- Contract tests pass.
- CI passes.
